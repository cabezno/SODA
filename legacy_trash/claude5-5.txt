ADVERTENCIA METODOLÓGICA — LEER ANTES DE INTERPRETAR ESTE INFORME
================================================================================

Este informe NO está basado en pruebas de ejecución en tiempo real del sistema.
Está basado exclusivamente en análisis estático del código fuente de SODA:
lectura de archivos .py, .js, .jsx, .html, configuraciones JSON/YAML y
comentarios en el código.

Qué significa esto en la práctica:

  ✓ Lo que SÍ refleja con fidelidad:
      - Qué funcionalidades están IMPLEMENTADAS en el código
      - Qué endpoints existen en server.py
      - Qué componentes hay en la UI (index.html, App.jsx)
      - Qué eventos WebSocket están definidos
      - Qué lógica tiene cada módulo del kernel
      - Qué indicadores, contadores y medidores están presentes en el HTML

  ✗ Lo que NO puede garantizar sin ejecución real:
      - Si cada endpoint responde correctamente en runtime
      - Si los drivers AI funcionan con las keys actuales
      - Si la UI renderiza sin errores de JS en el browser
      - Si el WebSocket conecta y entrega eventos correctamente
      - Si TTS/STT están operativos con los servicios instalados
      - Si el grafo DAG se actualiza visualmente como se espera
      - Si hay bugs de integración entre módulos no cubiertos por los tests

La única validación de ejecución real documentada en este informe está en la
Sección "PROYECTO DE PRUEBA GENERADO POR SODA" (ver abajo), donde se ejecutó
un proyecto generado por el propio sistema y se verificaron sus respuestas.

Si se requiere una auditoría basada en ejecución real de SODA completa,
es necesario levantar el servidor (lanzar_ui.bat), conectarse a localhost:8000,
y generar + ejecutar proyectos observando el comportamiento end-to-end.

1. PIPELINE PRINCIPAL
──────────────────────────────────────────────────────────────────────────────

Archivo:  kernel/orchestrator.py
Clase:    SodaOrchestrator
Entry:    run(description, project_name) → async

Fases en orden:

  CAP  → SkillMatcher + ProfileMatcher (Gemini): selecciona skills del proyecto
         skills/base/: skill_fastapi, skill_sqlite, skill_react, skill_jwt_auth,
         skill_rest_api. Cada skill tiene manifest.yaml + system_prompt.md + knowledge/

  WISDOM → WisdomAgent (Gemini): detecta ambigüedades en el request del usuario.
           Si hay preguntas sin resolver, genera USER_QUESTION y espera respuesta.

  REQ  → RequirementsInterviewer / ContextBuilder: genera blueprint.json con
         módulos, dependencias, tecnologías, comando de ejecución.

  ARCH → GlobalArchitect (Gemini): genera architecture.json con array de módulos.
         Campo "dependencias" = nombres de otros módulos (NO rutas de archivo).
         Prompt crítico: prompts/gemini/global_architect.md

  PLAN → DependencyGraph (Python puro): construye DAG con Kahn topological sort.
         ExecutionPlan ordena módulos para generación paralela donde sea posible.

  DEV  → CodeGenerator: Qwen (Ollama) intenta 3 veces por módulo.
         Si Qwen falla 3 veces, escala a Claude.
         Si Claude falla, guarda archivo con validated=False y continúa.
         ContextHealthMonitor: monitoreo pasivo de tokens y errores.

  BOOT → BootAgent: instala dependencias, boots el proyecto, detecta errores,
         aplica fixers determinísticos, escala a AI fixer si necesario.
         MAX_ROUNDS=5, health check TCP en puerto detectado.

  EVOLUTION → ProfileEvolutionEngine (Gemini): captura learnings en perfiles.
              profiles/base/: profile_web_fullstack, profile_backend_api,
              profile_general_dev.

Estado de cada fase: notificada via WebSocket (_notify event_type) con timeout=0.05s.

3. BOOT AGENT
──────────────────────────────────────────────────────────────────────────────

Archivo:  kernel/execution/boot_agent.py
Estado:   FUNCIONAL (refactorizado en esta sesión)

Constantes clave:
  MAX_ROUNDS             = 5
  HEALTH_CHECK_TIMEOUT   = 12s
  HEALTH_CHECK_INTERVAL  = 0.5s

Pipeline por ronda:
  1. Detectar stack (CMake > Cargo > Maven > .NET > Go > Node > Python)
     Prioridad explícita: evita Stack Mismatch (C++ + package.json)
  2. Instalar dependencias (npm install → --legacy-peer-deps → --force si falla)
  3. Bootar proceso
  4. Health check TCP: _extract_port() → _wait_for_port()
  5. Si hay errores → pipeline de fixers:
       a) _fix_missing_python_modules()   — ModuleNotFoundError
       b) _fix_ts_entry_point()           — Cannot find module '*.ts'
          Parchea package.json scripts → "npx tsx <entry>"
          Agrega tsx: "^4.19.0" a devDependencies
       c) _fix_env_connections()          — DB connection refused (:5432)
          Parchea DATABASE_URL → sqlite:///./app.db
       d) AI Fixer (Gemini → Claude)     — con _LIBRARY_USAGE_HINTS (12 libs)

Stuck-loop detection:
  - Boot:    si ronda N+1 tiene mismo error fingerprint y no hubo fix → break
  - Install: idem para install failures

JSON lenient parsing para respuesta del AI fixer:
  strict → JSONDecoder(strict=False) → strip control chars → parse

Stack Mismatch detection:
  _detect_stack_mismatch(): detecta package.json + archivos C++/Rust/Java
  Almacena warning, informa al AI fixer para que no use npm
