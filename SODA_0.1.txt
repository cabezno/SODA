1. ¿QUÉ ES SODA?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SODA toma una descripción en lenguaje natural y genera un proyecto de software
funcional completo, sin intervención humana durante la generación.

Entrada:  "Necesito una API REST con autenticación JWT y base de datos SQLite"
Salida:   Proyecto completo en projects/<id>/source/ con:
          - Código fuente validado
          - Tests automáticos (unit + funcionales)
          - Documentación generada
          - Blueprint, arquitectura y contratos tipados guardados
          - Boot + smoke tests ejecutados

SODA no es un autocomplete de código. Es un pipeline multi-agente determinístico
que orquesta modelos de IA especializados (Claude, Gemini, Qwen local) para
producir software real.

2. STACK TÉCNICO
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Lenguaje base:   Python 3.11.9
  OS:              Windows 11 Pro nativo (sin WSL2)
  Shell target:    bash (Unix paths en configuración)

  Modelos IA:
    - Claude Sonnet 4.6  (claude-sonnet-4-6)        → REQ, ARCH v2, DEV escal.
    - Claude Haiku 4.5   (claude-haiku-4-5)          → Conformance verify
    - Claude Opus 4.7    (claude-opus-4-7)            → Proyectos complejos
    - Gemini 2.5 Flash/Pro                            → CAP, WISDOM, ARCH v1
    - Qwen 2.5-coder:7b/14b (Ollama local)           → DEV primario

  Web framework:   FastAPI + uvicorn
  UI nativa:       pywebview + Monaco Editor
  Sandbox:         Docker Desktop (npipe Windows)
  Vectorial:       ChromaDB (persistencia local)
  Telegram:        python-telegram-bot v22 (@Soda_black_bot)
  Testing:         pytest 9.0.3

PIPELINE CORE
  [F01] Generación de proyectos desde descripción en lenguaje natural
  [F02] Selección automática de skills por keyword (31 skills disponibles)
  [F03] Selección automática de perfil de desarrollador (7 perfiles)
  [F04] Detección de riesgos y ambigüedades antes de generar (WisdomAgent)
  [F05] Generación de blueprint JSON (especificación funcional estructurada)
  [F06] Generación de topología de módulos (Gemini, DAG con snake_case IDs)
  [F07] Generación de MasterContract tipado (interfaces + data_types, por Claude)
  [F08] Clasificación de complejidad automática (simple/medium/complex)
  [F09] Selección de modelo según complejidad (Haiku/Sonnet/Opus)
  [F10] Planificación de ejecución con grafo de dependencias (Kahn topological sort)
  [F11] Detección y rotura automática de ciclos en el DAG
  [F12] Paralelismo: módulos sin dependencias generados simultáneamente
  [F13] Generación de código con escalación automática (9 niveles)
  [F14] Validación de sintaxis Python en Docker (py_compile)
  [F15] Inyección de contratos tipados en el generador de código
  [F16] Inyección de contexto de skills y perfil en cada generación
  [F17] Inyección de patrones aprendidos (learning context)
  [F18] Verificación de conformancia post-generación (Haiku audita c/módulo)
  [F19] Detección de código huérfano (anti-orphan, GoalIntegrityValidator)
  [F20] Validación de imports y dependencias Python
  [F21] Revisión de seguridad con Claude (SQL injection, XSS, etc.)
  [F22] Generación de unit tests contract-based (≥1 test por método del contrato)
  [F23] Generación de tests funcionales E2E por funcionalidad del blueprint
  [F24] Ejecución de suite de tests + triage automático de fallos
  [F25] Triage: clasifica BAD_TEST (regenera test) vs BAD_CODE (auto-fix)
  [F26] Validación de contrato API frontend ↔ backend
  [F27] Auditoría de lenguaje (reglas específicas: PY001 requirements.txt, etc.)
  [F28] Validación + auto-fix iterativo del código generado
  [F29] Boot Agent: instala deps, arranca proyecto, auto-repara si falla
  [F30] Smoke tests HTTP post-arranque
  [F31] Generación de documentación README
  [F32] Evolution: actualiza el perfil con patrones aprendidos tras cada proyecto
  [F33] Git commit automático en checkpoints del pipeline

OPERACIONES POST-GENERACIÓN
  [F34] modify(): aplica cambios a proyecto existente con clasificación de impacto
  [F35] GoalInterpreter: clasifica cambio (bug_fix/enhancement/structural/scope)
  [F36] ImpactAnalyzer: calcula módulos afectados transitivamente
  [F37] Branching automático para cambios estructurales (copia workspace)
  [F38] Comparación A/B entre rama y padre
  [F39] Promoción de rama ganadora
  [F40] refound(): comprime contexto y reinicia pipeline con descripción condensada
  [F41] resume(): retoma proyecto pausado desde el estado guardado

INFRAESTRUCTURA IA
  [F42] Driver abstraction: interfaz unificada para Claude/Gemini/Ollama/OpenAI
  [F43] Prompt Caching (Anthropic): ~90% ahorro en tokens de entrada
  [F44] Continuación automática de JSON truncado (Claude streaming)
  [F45] Probing dinámico de modelos Gemini (prueba en orden, cae al siguiente)
  [F46] Resolución lazy de modelo Ollama (ollama list async, cachea resultado)
  [F47] AIProviderHub: enrutamiento con fallback configurable por fase
  [F48] ContextHealthMonitor: monitoreo pasivo de tokens/errores sin bloquear
  [F49] Alertas automáticas cuando contexto crece o error rate sube
  [F50] Sugerencia automática de refundación cuando contexto es insostenible

VALIDACIÓN Y CONTRATOS
  [F51] ConsistencyValidator: naming consistente entre módulos
  [F52] CompletenessValidator: todos los módulos tienen interfaces
  [F53] DependencyValidator: no ciclos, deps resolubles
  [F54] NamingValidator: snake_case, convenciones por lenguaje
  [F55] ExtensibilityValidator: arquitectura permite extensión sin modificar existentes
  [F56] TraceabilityValidator: requerimientos → módulos → código
  [F57] TopologyConsistencyValidator: topology.json estructuralmente válido
  [F58] ContractAuditor: verifica que código generado cumple el contrato tipado
  [F59] AutoFixAgent: repara archivos con errores runtime usando Claude + contrato

MONITOREO Y COSTOS
  [F60] PerformanceTracker: métricas de duración/tokens/errores por fase
  [F61] UsageMonitor: registro de llamadas API (provider, role, tokens, tiempo)
  [F62] CostTracker: estimación de costo en USD por modelo y proyecto
  [F63] AlertManager: alertas por salud de contexto, error rate, slow calls

UI Y COMUNICACIÓN
  [F64] FastAPI server con 30+ endpoints REST
  [F65] WebSocket con broadcast en tiempo real a todos los clientes
  [F66] Monaco Editor integrado (UI nativa via pywebview)
  [F67] CopilotKit integration para chat IA en la UI
  [F68] Telegram Bot @Soda_black_bot con /pair /status /projects
  [F69] Notificaciones Telegram rate-limited (~20 msg/s, retry en 429)
  [F70] Temperatura de copilot configurable (baja/media/alta)

MEMORIA Y CONOCIMIENTO
  [F71] ProjectLineage: log append-only de todos los proyectos y ramas
  [F72] BranchManager: creación, promoción y comparación A/B de ramas
  [F73] ChromaDB: búsqueda semántica de patrones, skills, arquitecturas
  [F74] BehaviorObserver: captura de observaciones en JSONL (code_gen, escalations)
  [F75] KnowledgeBase: patrón library por lenguaje + framework

SANDBOX Y EJECUCIÓN
  [F76] DynamicEnvironment: venv aislado por proyecto (.soda_venv)
  [F77] DockerSandbox: contenedores ephemeral con límites (512MB, 1 CPU, 30s)
  [F78] ProjectRunner: orchestrator de ejecución (detect → install → run → smoke)
  [F79] StackDetector: detección automática de stack (Python/Node/Java/Rust/etc.)
  [F80] PortManager: gestión de puertos para proyectos con múltiples servicios

CAPACIDADES AVANZADAS
  [F81] LogCollector: recolección de logs del sistema para contexto de auto-fix
  [F82] VisualInspector: análisis visual de screenshots con Gemini (vision)
  [F83] WebResearcher: búsqueda web via Perplexity API
  [F84] UIDesignAgent: genera design_spec.json para proyectos frontend
  [F85] ContextBuilder: inyección contextual (system + user) con caché por rol

4. PIPELINE: 8 FASES EXPLICADAS

│ FASE 0 — CAPABILITIES                  ~5-10s               │
├──────────────────────────────────────────────────────────────┤
│ Driver:  Gemini Flash                                        │
│ Agentes: SkillMatcher + ProfileMatcher                       │
│ Input:   Descripción del proyecto                            │
│ Output:  Lista de skills + nombre de profile                 │
│                                                              │
│ SkillMatcher usa Gemini para extraer skills por keyword.     │
│ 31 skills disponibles (fastapi, react, jwt_auth, etc.)       │
│ ProfileMatcher elige el profile más alineado (7 disponibles) │
│ Los skills y profile se inyectan en TODAS las fases siguient │
└──────────────────────────────────────────────────────────────┘
         ↓
┌──────────────────────────────────────────────────────────────┐
│ FASE 0.5 — WISDOM                      ~5-10s               │
├──────────────────────────────────────────────────────────────┤
│ Driver:  Gemini Flash                                        │
│ Agente:  WisdomAgent                                         │
│ Input:   Descripción + skills + profile                      │
│ Output:  WisdomReport (riesgos, ambigüedades, advertencias)  │
│                                                              │
│ Detecta ambigüedades antes de invertir tiempo en generación. │
│ Ejemplo: "sistema de pagos" sin aclarar gateway → advierte.  │
│ Las observaciones se incluyen en el blueprint como contexto. │
└──────────────────────────────────────────────────────────────┘
         ↓
┌──────────────────────────────────────────────────────────────┐
│ FASE 1 — REQUIREMENTS                  ~10-20s              │
├──────────────────────────────────────────────────────────────┤
│ Driver:  Claude Sonnet                                       │
│ Rol:     requirements_interviewer                            │
│ Input:   Descripción + skills + profile + wisdom_report      │
│ Output:  blueprint.json                                      │
│                                                              │
│ blueprint.json contiene:                                     │
│   nombre_proyecto, funcionalidades[], stack_sugerido{},      │
│   modulos_principales[], estimacion_complejidad,             │
│   comando_ejecucion, comando_instalacion                     │
│                                                              │
│ BlueprintValidator verifica el schema antes de continuar.    │
└──────────────────────────────────────────────────────────────┘
         ↓
┌──────────────────────────────────────────────────────────────┐
│ FASE 2 — ARCHITECTURE                  ~35-70s              │
├──────────────────────────────────────────────────────────────┤
│ Sub-fase 2a: Topología (Gemini)                              │
│   Driver:  Gemini Pro/Flash                                  │
│   Rol:     global_architect                                  │
│   Output:  topology.json                                     │
│   Contenido: módulos con IDs snake_case, responsabilidades,  │
│              archivos_principales[], depende_de_ids[]        │
│                                                              │
│ Sub-fase 2b: MasterContract (Claude) — NUEVO en v0.1        │
│   Driver:  Claude (Haiku/Sonnet/Opus según complejidad)      │
│   Agente:  Architect (complexity-aware model selection)      │
│   Output:  master_contract.json                              │
│   Contenido: modules[] con interfaces tipadas                │
│              (name, parameters:{}, returns, description)     │
│              + data_types[] con schemas JSON                 │
│              + complexity_level + model_used                 │
│                                                              │
│ El ContractRefinementLoop ejecuta hasta 3 intentos con       │
│ Claude y 2 de fallback con Gemini. Si ambos fallan usa       │
│ architecture legacy de topology.json.                        │
│                                                              │
│ Validators activos: topology_consistency, dependency         │
│ Output legacy: architecture.json (compatibilidad v1)        │
└──────────────────────────────────────────────────────────────┘
         ↓
┌──────────────────────────────────────────────────────────────┐
│ FASE 3 — PLANNING                      <100ms               │
├──────────────────────────────────────────────────────────────┤
│ Driver:  Python puro (sin IA)                                │
│ Input:   master_contract.json > topology.json > architecture │
│ Output:  execution_plan.json                                 │
│                                                              │
│ DependencyGraph.break_cycles()     → DFS, elimina back-edges│
│ DependencyGraph.topological_sort_kahn() → Kahn's algorithm  │
│                                                              │
│ execution_plan.json:                                         │
│   levels: [["db", "auth"], ["api"], ["frontend"]]            │
│   order:  ["db", "auth", "api", "frontend"]                  │
│   parallelizable: true                                       │
│   broken_edges: []  (ciclos eliminados si los hubo)         │
│                                                              │
│ Pre-creación de venv en background (fire-and-forget).        │
└──────────────────────────────────────────────────────────────┘
         ↓
┌──────────────────────────────────────────────────────────────┐
│ FASE 3.5 — DESIGN (si proyecto frontend)   ~10-20s          │
├──────────────────────────────────────────────────────────────┤

└──────────────────────────────────────────────────────────────┘
         ↓
┌──────────────────────────────────────────────────────────────┐
│ FASE 4 — DEVELOPMENT                  ~5-15 min             │
├──────────────────────────────────────────────────────────────┤
│ Por cada módulo en orden topológico (niveles en paralelo):   │
│                                                              │
│ Para cada archivo del módulo:                                │
│   1. FileComplexityRouter clasifica complejidad del archivo  │
│   2. Inyecta contrato tipado (interfaces + data_types)       │
│   3. Inyecta skills_context + profile_context               │
│   4. Inyecta learning_context (patrones aprendidos)          │
│   5. Escalación de 9 niveles:                                │
│      L1: Qwen temp=0.2     L4: Gemini Flash int1             │
│      L2: Qwen temp=0.5     L5: Gemini Flash int2             │
│      L3: Qwen temp=0.7     L6: Gemini Flash int3             │
│                            L7: Claude Sonnet int1            │
│                            L8: Claude Sonnet int2            │
│                            L9: Claude Sonnet int3            │
│      Si L9 falla → guarda con validated=False y continúa    │
│   6. Validación sintaxis Python (Docker py_compile)          │
│   7. Inyección de metadata (goal_id en comentario)           │
│   8. BehaviorObserver.record_*() → JSONL append-only        │
│   9. Level runtime check (syntax + startup probe por nivel)  │
│                                                              │
│ Archivos generados → source/ en workspace del proyecto       │
└──────────────────────────────────────────────────────────────┘
         ↓
┌──────────────────────────────────────────────────────────────┐
│ FASE 4.V — CONFORMANCE VERIFY          ~30-60s              │
├──────────────────────────────────────────────────────────────┤
│ Driver:  Claude Haiku (rápido y barato)                      │
│ Agente:  ConformanceVerifier                                 │
│ Input:   source/ + master_contract.json + topology.json      │
│ Proceso: Para cada módulo, lee archivos_principales y        │
│          verifica que las firmas implementadas coinciden con  │
│          el contrato. Reescribe el archivo si no conforma.   │
│ Output:  Archivos corregidos in-place                        │
└──────────────────────────────────────────────────────────────┘
         ↓
┌──────────────────────────────────────────────────────────────┐
│ FASE 4.1 — IMPORT VALIDATION                                 │
│ FASE 4.2 — SECURITY REVIEW                                   │
│ FASE 4.3 — TEST GENERATION        ~20-40s (contract-based)  │
│ FASE 4.4 — RUN & TRIAGE TESTS                               │
│ FASE 4.5 — VALIDATION + AUTO-FIX  ~2-5 min                 │
│ FASE 4.6 — API CONTRACT CHECK                                │
│ FASE 4.7 — LANGUAGE AUDIT                                    │
├──────────────────────────────────────────────────────────────┤
│ Test Generation (4.3):                                       │
│   TestGenerator: genera <modulo>_test.py con ≥1 test        │
│     por método del contrato (contract-based testing)         │
│   FunctionalTestGenerator: genera test_e2e.py por feature    │

│                                                              │
│ Validation + Auto-fix (4.5):                                 │
│   ProjectValidator: instala deps, ejecuta proyecto           │
│   Si hay errores → AutoFixAgent (≤2 rondas de reparación)   │
│   _validate_and_maybe_regen: detecta módulos con errores     │

         ↓

│ DockerSandbox: tests TDD (advisory, no bloquea DONE)         │
│ VisualInspector: screenshot + análisis visual (opcional)     │

6. DRIVERS DE IA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CLAUDE (claude_driver.py)
  Modelo:    claude-sonnet-4-6 (por defecto), haiku-4-5, opus-4-7
  Features:
    - Streaming obligatorio (Anthropic API)
    - Prompt Caching: bloque cached_context → ~90% ahorro en tokens input
    - Continuación automática de JSON truncado (stop_reason="max_tokens")
    - max_tokens inteligente: Haiku=8k, Sonnet=64k, Opus=32k
    - Soporte imágenes base64 (vision)
    - Metadata pass-through para observability
  Config:    ANTHROPIC_API_KEY

GEMINI (gemini_driver.py)
  Modelos:   gemini-2.5-pro, gemini-2.5-flash, gemini-2.0-flash (en orden)
  Features:
    - Probing dinámico: prueba modelos en orden hasta que uno responda
    - Modelo preferido via GEMINI_MODEL env var o soda_config.json
    - Error classification: AUTH, RATE_LIMIT, OVERLOADED, BAD_REQUEST
    - Timeout: 120s (connect 10s)
    - Soporte imágenes base64
  Config:    GEMINI_API_KEY, GEMINI_MODEL (opcional)

OLLAMA / QWEN (ollama_driver.py)
  Modelos:   qwen2.5-coder:14b (preferido), qwen2.5-coder:7b (fallback)
  Features:
    - Resolución lazy async (ollama list en thread pool, cachea resultado)
    - Auto-selección 14b > 7b según lo disponible
    - Timeout 180s (Qwen típicamente 15-25s)
    - Error messages claros con sugerencia de ollama pull
  Config:    OLLAMA_BASE_URL (default: http://127.0.0.1:11434)

OPENAI (openai_driver.py)
  Modelos:   gpt-4-turbo, gpt-3.5-turbo
  Features:  Fallback opcional cuando otros providers fallan
  Config:    OPENAI_API_KEY

PROVIDER HUB (provider_hub.py)
  Enrutamiento configurable en soda_config.json:
    ai_routing: { "claude": ["claude","gemini","openai","ollama"] }
    ai_phase_provider: { "requirements_interviewer": "claude" }
  Lógica: primary → fallbacks en orden → si todos fallan, levanta excepción

ESCALACIÓN EN DEV (code_generator.py)
  Nivel 1-3: Qwen (temp 0.2/0.5/0.7)
  Nivel 4-6: Gemini Flash (3 intentos)
  Nivel 7-9: Claude Sonnet (3 intentos)
  Fallback final: guarda con validated=False, pipeline continúa

TEST GENERATOR (kernel/testing/test_generator.py):
  Genera unit tests en pytest para cada módulo.
  Con master_contract: inyecta bloque <contrato_del_modulo> con todas las
    interfaces tipadas. El prompt exige ≥1 test por método del contrato.
  Sin master_contract: genera tests heurísticos desde el código fuente.
  Template: prompts/claude/test_engineer.md

FUNCTIONAL TEST GENERATOR (kernel/testing/functional_test_generator.py):
  Genera tests E2E HTTP desde blueprint.funcionalidades.
  Usa httpx para llamadas HTTP a la API.
  Primero intenta Gemini, fallback a Claude.
  Genera tests/test_functional_e2e.py.
  Templates: prompts/gemini/functional_test_engineer.md,
             prompts/claude/functional_test_engineer.md

TEST TRIAGE (kernel/testing/test_triage.py):
  Clasifica fallos de tests en 3 categorías:

  BAD_TEST:  El test es incorrecto (no el código)
    Señales: ImportError en test_, fixture not found, SyntaxError en test_,
             Cannot find module desde test
    Acción:  Regenera el archivo de test

  BAD_CODE:  El código bajo test tiene el bug
    Señales: AssertionError, TypeError, KeyError, 4xx/5xx HTTP status,
             NotImplementedError
    Acción:  AutoFixAgent repara el archivo fuente

  UNKNOWN:   No se puede clasificar
    Acción:  Registra para análisis manual

  TriageResult: (verdict, confidence, matched_pattern, suggestion)
  BatchTriageReport: (results[], bad_test_count, bad_code_count, unknown_count)

CONTEXT HEALTH MONITOR (kernel/intelligence/context_health_monitor.py):
  Monitoreo pasivo, no bloquea el pipeline.
  Umbrales calibrados:
    TOKEN_WARN_THRESHOLD = 80,000 tokens (~80% del límite 100k)
    SLOW_CALL_S          = 30s (Qwen normal: 15-25s)
    ERROR_RATE_WARN      = 0.50 (evita falso positivo en burst Qwen×3→Claude)
    ROLLING_WINDOW       = 15 llamadas
  Niveles de salud:
    0 = healthy
    1 = observe (llamadas lentas)
    2 = warn (tokens altos o error rate)
    3 = critical (contexto creciendo sostenidamente → sugiere refund)

PERFORMANCE TRACKER (kernel/monitoring/performance_tracker.py):
  Registra duración/tokens/errores por fase.
  Genera reporte al final de cada pipeline.
  record_gemini_phase(), record_claude_phase()

COST TRACKER (kernel/monitoring/cost_tracker.py):
  Precios por modelo (USD/1M tokens):
    Claude Sonnet: $3.00 input / $15.00 output
    Claude Haiku:  $0.80 input / $4.00 output
    Claude Opus:   $15.00 input / $75.00 output
    Gemini 2.5 Flash: $0.075 input / $0.30 output
    Qwen local:    $0.00

USAGE MONITOR (kernel/monitoring/usage_monitor.py):
  Log de todas las llamadas (provider, role, tokens, duración).
  get_summary(): total_calls, total_tokens, by_provider, by_role, avg_duration

ALERT MANAGER (kernel/monitoring/alert_manager.py):
  Emite alertas cuando ContextHealthMonitor reporta nivel ≥ 2.
  Alertas enviadas por: WebSocket (UI) + Telegram + print

    - Contenedores ephemeral (se eliminan tras ejecución)
    - Validación de sintaxis Python (py_compile dentro del contenedor)

DYNAMIC ENVIRONMENT (kernel/sandbox/dynamic_env.py):
  Venv aislado por proyecto (.soda_venv en workspace)
  Lifecycle:
    1. ensure_venv()         → crea .soda_venv si no existe
    2. install_requirements() → pip install desde requirements.txt
    3. run_syntax_check()    → py_compile todos los .py
    4. run_project()         → ejecuta entry point
    5. parse_errors()        → extrae file/line de tracebacks
  Timeouts: venv=60s, install=180s, exec=60s

BOOT AGENT (kernel/execution/boot_agent.py):
  Detecta stack → instala deps → arranca → auto-repara si falla
  Soporta: Python, Node.js, Java, Rust, Go, C#, C++, Flutter

PROJECT RUNNER (kernel/execution/project_runner.py):
  detect_stack → venv/env → install → run → smoke test
  install_timeout=300s, run_timeout=60s

    4. Registra parent_id en lineage del nuevo proyecto
