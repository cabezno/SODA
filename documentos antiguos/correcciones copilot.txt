HOJA DE RUTA - CORRECCIONES COPILOT

Objetivo
--------
Aplicar correcciones al sistema de revision con Copilot sin romper el pipeline.
Esta version de la hoja ya incorpora el estado actual del repo: varios bugs del
diagnostico inicial ya parecen corregidos o cubiertos por tests, asi que la prioridad
real pasa a ser alinear el comportamiento entre fases y hacer mas accionable la salida
de Copilot.

CONTEXTO TECNICO MINIMO PARA CLAUDE CODE
----------------------------------------
Antes de implementar nada, Claude Code debe asumir este contexto del repo actual:

- El entry point principal sigue siendo SodaOrchestrator en kernel/orchestrator.py,
  pero buena parte de la logica de fases ya no vive ahi: requirements, architecture,
  planning y validation estan en kernel/orchestration/phase_mixin.py.
- El consultor de Copilot esta en kernel/intelligence/copilot_consultant.py y hoy
  sigue trabajando principalmente con un contrato simple compatible con
  has_suggestion, message y changes.
- El orquestador sigue usando _copilot_suggest(...) como punto comun de evaluacion,
  pero Development tiene un loop mas fuerte que el resto de las fases.
- El comportamiento que hoy parece realmente pendiente no es rehacer fixes viejos,
  sino alinear Validation entre run() y resume(), enriquecer el contrato de Copilot,
  centralizar la decision y luego integrar esa decision en fases concretas.
- Ya existe red de seguridad relevante en tests/test_unit.py para fallbacks async,
  rama non-software, seleccion por fase y /api/config. Esa base debe reutilizarse.
- El workspace esta sucio y tiene ruido fuera del objetivo inmediato. No usar el estado
  global del repo como señal principal si el slice puede validarse con tests locales.

ANALISIS DE PRECAUCIONES PARA NO IMPACTAR NEGATIVAMENTE EL CODIGO
----------------------------------------------------------------
Estas son las precauciones que Claude Code debe considerar como analisis previo obligatorio:

1. Riesgo de tocar el archivo equivocado
----------------------------------------
El mayor riesgo inmediato es modificar solo kernel/orchestrator.py y olvidar que varias
fases reales viven en kernel/orchestration/phase_mixin.py. Si el cambio afecta requirements,
architecture, planning o validation, hay que revisar ambos puntos antes de editar.

2. Riesgo de reabrir bugs ya cerrados
-------------------------------------
No reimplementar fixes del diagnostico inicial sin prueba actual de regresion.
En especial, no tocar de nuevo fallback async, rama non-software o /api/config salvo que
un test o una lectura puntual demuestre que volvieron a romperse.

3. Riesgo de romper compatibilidad del contrato Copilot
-------------------------------------------------------
Si cambia la salida de CopilotConsultant, los consumidores actuales pueden romperse en cadena.
Por eso el contrato nuevo debe introducirse primero como normalizacion compatible hacia atras
y solo despues consumirse en orchestrator y phase_mixin.

4. Riesgo de divergencia entre run() y resume()
-----------------------------------------------
No corregir solo uno de los dos caminos si el bug pertenece a validation.
La asimetria actual entre run() y resume() es justamente uno de los problemas a resolver,
asi que cualquier fix de validation debe verificarse en ambos caminos o extraerse a una ruta comun.

5. Riesgo estructural en Architecture y Planning
------------------------------------------------
Architecture no es una fase aislada: alimenta GoalTree, ExecutionPlan y Development.
Si se reemplaza un comportamiento advisory por regeneracion o reparacion real, hay que verificar
que la salida siga siendo consumible por planning y por las fases siguientes antes de avanzar.

6. Riesgo de degradar el mejor loop actual
------------------------------------------
Development ya tiene el loop mas fuerte del sistema: generar -> revisar -> regenerar -> verificar.
No usar Development como primer lugar de experimentacion del contrato enriquecido. Ese ajuste va
al final, cuando el manejo comun y las fases previas ya esten estables.

7. Riesgo de mezclar fix funcional con refactor
-----------------------------------------------
No combinar en un mismo slice:
  - alineacion run()/resume(),
  - rediseño del contrato Copilot,
  - integracion de fases,
  - limpieza de providers/config,
  - refactor estetico.
Si el cambio necesita mas de una de esas cosas, dividirlo.

8. Riesgo de validar demasiado tarde
------------------------------------
La validacion tiene que ser inmediata y acotada. El orden correcto es:
  - test mas cercano al cambio,
  - regresion del subsistema,
  - solo despues una regresion mas amplia.
No usar una validacion global como sustituto del test discriminante del slice.

9. Riesgo de tocar archivos que no forman parte del objetivo
------------------------------------------------------------
No tocar contenido de projects/.
No usar .soda_backups/ ni .webview_cache/ como superficie de edicion.
Esos directorios pueden servir como referencia historica o ruido del workspace, pero no deben
entrar en el cambio salvo instruccion explicita.

10. Riesgo de interpretar el repo sucio como fallo del slice
------------------------------------------------------------
El repo puede tener cambios no relacionados. No intentar limpiarlos ni revertirlos.
La validacion del slice debe basarse en el archivo tocado, el test cercano y el comportamiento
objetivo, no en dejar el repositorio completo sin cambios.

11. Criterio de avance seguro
-----------------------------
Claude Code solo puede pasar a la siguiente fase si el slice actual queda verde.
Si una validacion falla, la obligacion es reparar ese mismo slice o revertirlo, no abrir otro frente.

INSTRUCCION OPERATIVA CONSOLIDADA PARA CLAUDE CODE
--------------------------------------------------
Esta hoja no es descriptiva. Es una secuencia de ejecucion.
Claude Code debe seguir siempre este protocolo y no desviarse de el salvo que una validacion
lo obligue a corregir el mismo slice.

Definicion de "verde"
----------------------
Un slice queda verde solo si se cumplen las tres condiciones:
  1. El cambio no introduce errores nuevos.
  2. El test mas cercano al cambio pasa.
  3. La regresion relevante del subsistema sigue pasando.

Alcance
-------
- Trabajar solo sobre el codigo fuente del repo.
- No tocar contenido de projects/.
- No reabrir bugs que hoy ya estan resueltos salvo que una validacion los vuelva a romper.
- No mezclar estas correcciones con refactors no relacionados.
- Mantener cambios pequenos, reversibles y verificables.

Protocolo obligatorio por slice
-------------------------------
1. Antes de tocar codigo, leer el archivo objetivo y el test mas cercano.
2. Confirmar que el problema sigue vigente en el repo actual y no es un hallazgo viejo.
3. Formular el bug concreto a corregir y elegir la validacion minima que puede falsarlo.
4. Hacer el cambio mas pequeno posible.
5. Ejecutar primero la validacion minima del slice.
6. Si pasa, ejecutar la regresion relacionada del subsistema.
7. Si ambas pasan, cerrar el slice y avanzar.
8. Si alguna falla, reparar ese mismo slice o volver atras antes de abrir otro frente.

Regla unica de seguridad
------------------------
No encadenar varios cambios grandes sin una validacion acotada entre medio.

Regla unica sobre tests
-----------------------
Antes de crear tests nuevos, revisar la cobertura ya existente en tests/test_unit.py y
tests/test_pipeline.py. Reutilizar o extender regresiones ya presentes antes de duplicar
casos con otro nombre o en otro archivo.

REGLAS PARA NO ROMPER EL CODIGO
===============================

1. Trabajar por slices chicos
-----------------------------
No mezclar en el mismo cambio:
  - alineacion validation,
  - redisenos de contrato,
  - integraciones de fases,
  - limpieza de providers o config,
  - refactors esteticos.

2. Validar despues de cada cambio sustantivo
--------------------------------------------
Orden recomendado:
  a) test mas cercano al cambio,
  b) test del subsistema,
  c) pytest completo,
  d) chequeo manual puntual solo si hace falta.

3. No cambiar APIs o contratos sin actualizar call sites en el mismo cambio
---------------------------------------------------------------------------
Si cambia una firma o un contrato estructurado, actualizar todos los puntos de uso
en la misma tanda y cubrirlos con test.

4. Si una validacion falla, reparar el mismo slice antes de abrir otro frente
-----------------------------------------------------------------------------
No seguir tocando mas capas si el test mas cercano todavia esta rojo.

5. Mantener compatibilidad hacia atras cuando sea barato
--------------------------------------------------------
Especialmente en la salida de Copilot y en la configuracion del servidor.

6. No tocar Development temprano
--------------------------------
Primero alinear validation y fases previas. Development va al final.

7. Estrategia de retroceso si un slice rompe codigo existente
------------------------------------------------------------
Si el test mas cercano al cambio falla y la causa no se corrige en el mismo slice:
  - revertir el ultimo cambio local de ese slice,
  - volver al ultimo estado verde,
  - reducir el alcance,
  - reintentar con una correccion mas pequena.

No abrir una fase nueva mientras el slice actual siga rojo.

8. Preferir ampliar regresiones existentes antes que crear suites paralelas
--------------------------------------------------------------------------
Para esta hoja de ruta ya existe base de regresion util para:
  - fallback async en capabilities,
  - rama non-software,
  - /api/config,
  - overrides de provider por fase.

Primero extender esos tests. Solo crear archivos nuevos si el comportamiento a cubrir no
encaja razonablemente en la suite actual.

9. Formato de entrega esperado por slice
----------------------------------------
Al cerrar cada slice, Claude Code debe dejar claro:
  - que archivos toco,
  - que bug resolvio,
  - que test corrio,
  - si el slice quedo verde o no.

10. No considerar un cambio "terminado" solo porque compila
-----------------------------------------------------------
Para esta hoja de ruta, terminado significa:
  - bug corregido,
  - regresion relevante verde,
  - sin degradacion visible en tests cercanos.

ANEXO - HOJA DE RUTA PARA VALIDACION, INSTALACION Y ARRANQUE
============================================================

Objetivo
--------
Corregir el tramo final del pipeline donde hoy se mezclan validacion estatica,
instalacion de dependencias, arranque del proyecto y smoke checks, sin convertir
errores de entorno en falsos bloqueos ni romper el cierre actual del pipeline.

Estado actual del repo que esta hoja asume como punto de partida
----------------------------------------------------------------
- _phase_validation en kernel/orchestration/phase_mixin.py delega en
  kernel/project_validator.py.
- ProjectValidator instala dependencias y corre un check de build o compilacion
  segun stack.
- _validate_and_maybe_regen en kernel/orchestrator.py ya existe y puede disparar
  regeneracion dirigida si los errores quedan concentrados por modulo.
- El orquestador ya no cierra siempre en DONE: run() y resume() usan
  _can_reach_done(...), pero ese guard aun es conservador y solo mira ciertos
  patrones estructurales de error.
- BootAgent intenta instalar, arrancar, capturar logs y corregir con IA.
- ProjectRunner vuelve a instalar, lanzar y hacer smoke HTTP.
- DockerSandbox existe, pero hoy no debe asumirse como prueba fuerte de ejecucion
  real del proyecto.

Problema real a corregir
------------------------
No es que SODA no mire nada. Mira muchas cosas, pero las mira desde varias capas
distintas y no todas tienen autoridad para bloquear DONE.

Hoy el riesgo principal es este:
- un mismo fallo de dependencias puede aparecer en ProjectValidator, BootAgent y
  ProjectRunner;
- el smoke HTTP puede avisar fallo pero no necesariamente bloquear el pipeline;
- DockerSandbox puede dar una falsa sensacion de cobertura;
- el criterio de cierre mezcla errores del codigo generado con problemas del entorno.

Principio rector de esta hoja
-----------------------------
Primero separar evidencia de ejecucion real de evidencia estatica.
Despues definir que tipos de error bloquean DONE.
Recien al final endurecer el cierre del pipeline.

Regla de seguridad critica
--------------------------
No endurecer DONE antes de clasificar los errores.
Si se hace al reves, se van a bloquear proyectos validos por:
  - Docker no disponible,
  - dependencias externas no presentes en el host,
  - servicios o API keys ausentes,
  - stacks donde el smoke HTTP no es la senal correcta.

  - la app arranca pero responde 404/500 en un probe inicial
  - warnings de startup sin crash

Regla de esta fase
------------------
No cambiar aun _can_reach_done().
Primero escribir tests de decision con fixtures pequenos de errores.

Condicion de cierre
-------------------
- Existe una tabla de decision verificable para "bloquea DONE" versus "solo advierte".


FASE R2 - HACER DE _can_reach_done() UNA DECISION EXPLICITA Y TESTEADA
=======================================================================

Objetivo
  Reemplazar el guard actual por una decision basada en la taxonomia definida.

Archivo objetivo

- kernel/orchestrator.py
- tests/test_unit.py

Cambios esperados
-----------------
- Mantener la firma pequena y local.
- Basar la decision en clasificacion, no solo en substring sueltos.

Orden correcto

FASE R3 - ELIMINAR DOBLE O TRIPLE RESPONSABILIDAD SIN CAMBIAR AUN EL RESULTADO FINAL
======================================================================================

Objetivo
  Reducir chequeos redundantes para que cada capa tenga una responsabilidad clara.

Distribucion recomendada
------------------------
- ProjectValidator
  fuente de verdad para install + build/check estatico.

- BootAgent
  fuente de verdad para install + boot + captura de errores de arranque + fix loop.

- ProjectRunner
  fuente de verdad para launch final + smoke HTTP + smoke suite.

Regla de esta fase
------------------
No borrar una capa completa en el primer cambio.
Primero marcar una como autoritativa y convertir las otras en advisory donde corresponda.

Slice sugerido
--------------
- Evitar que ProjectRunner vuelva a "instalar" si BootAgent ya dejo evidencia valida
  de install para ese intento.
- Evitar que el orquestador interprete tres veces el mismo fallo como tres problemas distintos.

Condicion de cierre
-------------------
- Install, boot y smoke ya no aparecen duplicados como si fueran fallos independientes.


FASE R4 - ENDURECER EL SMOKE PARA QUE LA SENAL SEA UTIL
=======================================================

Objetivo
  Hacer que el smoke represente mejor "la app esta viva" sin romper stacks no HTTP.

Problema actual
---------------
- El smoke de ProjectRunner acepta cualquier HTTP entre 200 y 499.
- Eso sirve para detectar que hay algo escuchando, pero no prueba salud funcional.

Estrategia segura
-----------------
- No volver el smoke mas estricto para todos los stacks de una vez.
- Introducir primero un modo por stack o por tipo de proyecto.
- Mantener "probe basico" como fallback.

Orden recomendado
-----------------
1. agregar metadata de probe esperada,
2. soportar excepciones por stack,
3. endurecer solo donde haya evidencia clara de endpoint raiz esperable.

Condicion de cierre
-------------------
- El smoke deja de ser enganoso sin pasar a ser una fuente masiva de falsos negativos.


FASE R5 - TRATAR DOCKER SANDBOX COMO ADVISORY HASTA QUE SEA CONFIABLE
=====================================================================

Objetivo
  Evitar que una capa incompleta se perciba como validacion fuerte.

Regla de esta fase
------------------
- Si DockerSandbox no ejecuta realmente el test suite esperado, no usarlo como criterio
  de bloqueo ni como evidencia principal de calidad.
- Mientras tanto, degradarlo a chequeo advisory y dejarlo claro en logs/reportes.

Dos opciones validas
--------------------
- Opcion A: dejarlo explicitamente como advisory hasta completarlo.
- Opcion B: completarlo de verdad y recien entonces promoverlo en el pipeline.

Condicion de cierre
-------------------
- Docker deja de vender una garantia que hoy no puede sostener.


FASE R6 - CIERRE FINAL DEL PIPELINE BASADO EN EVIDENCIA MINIMA SUFICIENTE
=========================================================================

Objetivo
  Definir la condicion final de exito del tramo runtime.

Propuesta de cierre seguro
--------------------------
Marcar DONE solo si se cumple esta evidencia minima:

1. Validation no deja errores bloqueantes del codigo generado.
2. BootAgent no reporta crash estructural del arranque.
3. El smoke aplicable al stack pasa, o el stack esta explicitamente marcado como no-HTTP.

Marcar FAILED o estado equivalente si:
--------------------------------------
- hay error bloqueante del codigo,
- el arranque rompe de forma estructural,
- o el smoke obligatorio del stack falla de forma persistente.

Mantener HEALTH_WARN si:
------------------------
- el problema es de entorno,
- el proyecto requiere configuracion externa,
- o la verificacion disponible no alcanza para una conclusion mas fuerte.

Condicion de cierre
-------------------
- El DONE final deja de ser "compilo algo" y pasa a significar "hay evidencia minima suficiente de que el proyecto generado es ejecutable".


TESTS MINIMOS RECOMENDADOS PARA ESTA HOJA
=========================================

1. Tests de clasificacion
-------------------------
- errores estructurales del codigo bloquean DONE.
- errores de entorno no bloquean DONE.

2. Tests de decision final
--------------------------
- run() no marca DONE cuando _can_reach_done() devuelve False.
- resume() mantiene el mismo criterio.
- import_from_code() no queda desalineado.

3. Tests de smoke
-----------------
- un stack HTTP con connection_error queda en warning o fail segun clasificacion.
- un stack no-HTTP no se penaliza por no tener probe HTTP valido.

4. Tests de no regresion
------------------------
- la validacion comun sigue pasando.
- no se rompe el loop de targeted regeneration.
- no se toca el timeout critico de _notify().

==========================================

Esta correccion se considera bien hecha solo si:

- y los tests cercanos siguen verdes despues de cada slice.
