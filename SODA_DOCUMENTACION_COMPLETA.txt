────────────────────────────────────────────────────────────────────────────────
 1. DESCRIPCIÓN GENERAL DEL SISTEMA
────────────────────────────────────────────────────────────────────────────────

SODA es un sistema multi-agente de desarrollo de software que orquesta múltiples
modelos de IA (Claude, Gemini, Qwen/Ollama) para generar proyectos completos de
software a partir de una descripción en lenguaje natural. Corre en Windows 11
nativo (sin WSL2) y expone una interfaz web + webview embebida.

Stack tecnológico:
  - Python 3.11.9 en Windows 11
  - FastAPI + uvicorn como servidor HTTP/WebSocket
  - pywebview (Edge Chromium) como ventana nativa de escritorio
  - Monaco Editor en el frontend (editor de código)
  - Docker Desktop (npipe Windows) para validación de sintaxis
  - python-telegram-bot v22 para notificaciones móviles

 2. PIPELINE COMPLETO: FASES DE EJECUCIÓN
────────────────────────────────────────────────────────────────────────────────

El pipeline sigue este orden determinístico:

  CAP → WISDOM → REQ → ARCH → PLAN → DEV → EVOLUTION → DONE

Detalle de cada fase:

  CAP (Capabilities)
    Modelo: Gemini
    Qué hace: Analiza la descripción del usuario y selecciona qué skills y
    perfiles de desarrollador son más apropiados para el proyecto.
    Agentes: skill_matcher, profile_matcher
    Salida: lista de skills activos + perfil seleccionado

  WISDOM
    Modelo: Gemini
    Qué hace: Detecta ambigüedades o puntos poco claros en la descripción
    antes de proceder. Si encuentra ambigüedad, pregunta al usuario.
    Agente: wisdom_agent
    Salida: confirmación de que la descripción es suficientemente clara,
    o preguntas de clarificación al usuario.

  REQ (Requirements)
    Modelo: Claude (claude-sonnet-4-6)
    Qué hace: Entrevista al usuario (si interactive_mode=True) y genera
    el blueprint.json con módulos, stack sugerido, endpoints y
    funcionalidades.
    Agente: requirements_interviewer
    Salida: blueprint.json

  ARCH (Architecture)
    Modelo: Gemini
    Qué hace: Lee el blueprint y genera la arquitectura maestra con módulos,
    interfaces, tipos de datos, contratos entre módulos y tipos de error.
    Agente: global_architect
    Salida: architecture.json (el contrato maestro del proyecto)

  PLAN (Planning)
    Tecnología: Python puro (sin IA)
    Qué hace: Construye el grafo de dependencias entre módulos (DAG), rompe
    ciclos si los hay, y genera el plan de ejecución por niveles donde
    los módulos del mismo nivel pueden generarse en paralelo.
    Salida: execution_plan.json con niveles de ejecución

  DEV (Development)
    Modelos: Qwen (local) → Gemini → Claude (escalación)
    Qué hace: Genera el código de cada módulo siguiendo el plan. Aplica
    el loop Qwen↔Copilot para revisar y corregir iterativamente.
    Salida: archivos de código en projects/{id}/source/

  EVOLUTION
    Modelo: Gemini
    Qué hace: Captura learnings del proyecto completado y actualiza el
    perfil del desarrollador para futuros proyectos.
    Agente: profile_evolution
    Salida: actualizaciones en profiles/

  DONE
    Estado final. Se emite evento DONE vía WebSocket y Telegram.


────────────────────────────────────────────────────────────────────────────────
 3. ESCALACIÓN DE CÓDIGO: SISTEMA DE 9 NIVELES
────────────────────────────────────────────────────────────────────────────────

Cada archivo se intenta generar en hasta 9 niveles antes de rendirse:

  Nivel 1-3 │ Qwen (Ollama, local)
  ──────────┼───────────────────────────────────────────────────────────────
            │ Modelo: qwen2.5-coder:14b (si disponible) o qwen2.5-coder:7b
            │ 3 intentos. Rápido, gratuito, sin red. Ideal para archivos
            │ simples: configuraciones, modelos de datos, utilidades.

  Nivel 4-6 │ Gemini (Google Cloud)
  ──────────┼───────────────────────────────────────────────────────────────
            │ Modelo: gemini-2.5-pro o gemini-2.5-flash
            │ 3 intentos. Se activa cuando Qwen falla 3 veces.
            │ Nivel 6 usa Claude Haiku como variante.

  Nivel 7-9 │ Claude (Anthropic Cloud)
  ──────────┼───────────────────────────────────────────────────────────────
            │ Modelo: claude-sonnet-4-6
            │ 3 intentos. Máxima capacidad de razonamiento.
            │ Si los 9 niveles fallan, el archivo se guarda con
            │ validated=False y el pipeline continúa (no aborta).

Router de complejidad: el sistema clasifica automáticamente cada archivo
según su complejidad. Los archivos complejos saltan Qwen directamente y
empiezan en Gemini (nivel 4).


────────────────────────────────────────────────────────────────────────────────
 4. MODELOS DE IA: PARÁMETROS Y CONFIGURACIÓN
────────────────────────────────────────────────────────────────────────────────

──── Claude (anthropic SDK) ────────────────────────────────────────────────────

  Modelo principal:  claude-sonnet-4-6
  Modelo fallback:   claude-haiku-4-5-20251001

  Límites de tokens por modelo:
    claude-haiku-4-5-20251001   →  8.192 tokens
    claude-haiku-4-5            →  8.192 tokens
    claude-sonnet-4-6           → 64.000 tokens
    claude-sonnet-4-5           → 64.000 tokens
    claude-opus-4-7             → 32.000 tokens
    claude-opus-4-5             → 32.000 tokens

  Temperatura: DEPRECATED en Claude 4.x. El parámetro se acepta por
  compatibilidad de API pero NO se envía a la API de Anthropic.

  Streaming: activado siempre (requerimiento de Anthropic para max_tokens
  grandes).

  Prompt caching (cache_control: ephemeral):
    - El system prompt se cachea en cada llamada.
    - Si se pasa cached_context (contexto previo), también se cachea.
    - El mensaje del usuario no se cachea (varía en cada llamada).
    - Reduce costos entre 50-70% en llamadas repetidas al mismo rol.

  Continuation loop: si la respuesta se trunca (max_tokens alcanzado),
  el driver hace llamadas adicionales para completar la respuesta.

──── Gemini (google-genai SDK) ─────────────────────────────────────────────────

  Modelos disponibles: gemini-2.5-pro, gemini-2.5-flash, gemini-2.0-flash
  Usado en: CAP, WISDOM, ARCH, DEV (escalación media), EVOLUTION

──── Qwen / Ollama (local) ─────────────────────────────────────────────────────

  Modelos: qwen2.5-coder:14b (preferido), qwen2.5-coder:7b (fallback)
  Base URL: http://localhost:11434 (configurable via OLLAMA_BASE_URL)
  Usado en: DEV (primera línea de generación de código)

──── Routing y cadenas de fallback ─────────────────────────────────────────────

  Definido en soda_config.json → "ai_routing":
    "claude":  ["claude", "gemini", "ollama"]
    "gemini":  ["gemini", "claude", "ollama"]
    "ollama":  ["ollama", "claude", "gemini"]

  Si el proveedor primario falla, el sistema intenta el siguiente en la cadena.

──── Asignación de proveedor por fase ──────────────────────────────────────────

  Definido en soda_config.json → "ai_phase_provider":
    requirements_interviewer  → claude
    global_architect          → gemini
    docs_generator            → claude

────────────────────────────────────────────────────────────────────────────────
 7. GRAFO DE DEPENDENCIAS Y PLANIFICACIÓN
────────────────────────────────────────────────────────────────────────────────

Clase: DependencyGraph (kernel/dependency_graph.py)
Algoritmo: Kahn's topological sort con detección de ciclos por DFS

Flujo:
  1. Se construye el grafo de adyacencia desde architecture.json
     (campo "dependencias" de cada módulo debe contener nombres exactos
     de otros módulos, NO rutas de archivo ni librerías externas).
  2. _find_back_edges(): DFS que detecta aristas que forman ciclos.
  3. break_cycles(): elimina las aristas de ciclo hasta obtener un DAG.
     Itera hasta len(grafo) veces para garantizar terminación.
  4. build_execution_plan(): Kahn's algorithm que agrupa módulos en niveles.
     Módulos en el mismo nivel no tienen dependencias entre sí → paralelos.
  5. Retorna ExecutionPlan con:
     levels          — lista de grupos de módulos paralelos
     order           — orden topológico plano
     parallelizable  — True si hay ≥2 módulos en algún nivel
     broken_edges    — aristas eliminadas para romper ciclos

Ejemplo de plan de 3 niveles:
  Nivel 0: [db_service, config]          ← sin dependencias → paralelos
  Nivel 1: [auth_service, user_service]  ← dependen de nivel 0
  Nivel 2: [api_router]                  ← depende de nivel 1

 8. MÓDULOS DE INTELIGENCIA
────────────────────────────────────────────────────────────────────────────────

──── ContextHealthMonitor ──────────────────────────────────────────────────────

Archivo: kernel/intelligence/context_health_monitor.py
Función: monitoreo pasivo del contexto de IA durante el pipeline.

Umbrales calibrados:
  TOKEN_WARN_THRESHOLD    = 80.000   (~80% del límite de 100k)
  TOKEN_REFOUND_THRESHOLD = 60.000   (si se supera sostenidamente → refound)
  SLOW_CALL_S             = 30s      (llamada lenta: Qwen normal 15-25s)
  ERROR_RATE_WARN         = 0.50     (>50% errores en ventana rodante)
  ROLLING_WINDOW          = 15       (llamadas en ventana para tasa de error)
  GROWTH_CHECK_WINDOW     = 5        (snapshots para detectar crecimiento)
  GROWTH_STEP_TOKENS      = 3.000    (mínimo de crecimiento por checkpoint)

Niveles de salud:
  0 = ok        → todo normal
  1 = observe   → métricas en zona de atención, sin acción necesaria
  2 = warn      → degradación notable, el pipeline recibe sugerencia
  3 = critical  → se sugiere refound (compresión de contexto)

Estimación de tokens: len(response) // 4

──── GoalInterpreter ───────────────────────────────────────────────────────────

Archivo: kernel/intelligence/goal_interpreter.py
Función: clasifica una solicitud de modificación del usuario.

Flujo:
  1. _check_ambiguity() con Claude: ¿es la solicitud ambigua?
  2. Si ambigua: pide clarificación al usuario (USER_QUESTION event).
  3. Tarea completa a Claude para clasificar y planificar la modificación.
  4. Retorna ModificationPlan con:
     change_type          — tipo de cambio
     affected_modules     — módulos que se modifican
     new_modules          — módulos nuevos (si aplica)
     requires_regeneration — True/False
     regeneration_scope   — "full" | "partial" | "none"
     impact_summary       — descripción del impacto

Tipos de cambio:
  parameter    → cambio de config/valor (bajo impacto)
  behavior     → cambio funcional (impacto medio)
  structural   → renombrar/dividir/fusionar módulos (alto impacto)
  scope        → agregar/eliminar funcionalidad (alto impacto)
  new_module   → módulo independiente nuevo (impacto medio)

──── ImpactAnalyzer ────────────────────────────────────────────────────────────

Archivo: kernel/intelligence/impact_analyzer.py
Función: análisis transitivo de impacto dado un ModificationPlan.

Flujo:
  1. Construye grafo de dependencias desde architecture.json.
  2. Claude analiza el plan de modificación y el grafo.
  3. Retorna ImpactReport con:
     directly_affected     — módulos directamente afectados
     transitively_affected — módulos afectados por propagación
     unaffected            — módulos que no cambian
     regeneration_order    — orden topológico de regeneración
     risk_level            — "low" | "medium" | "high"
     risk_reason           — justificación del nivel de riesgo


────────────────────────────────────────────────────────────────────────────────
 9. SISTEMA DE BRANCHING (RAMAS DE PROYECTO)
────────────────────────────────────────────────────────────────────────────────

Archivo: kernel/lineage/branching.py

Cuándo se crea una rama:
  Se activa cuando change_type ∈ {structural, scope, new_module}
  Y requires_regeneration = True.

  La lógica: cambios estructurales pueden romper el proyecto activo.
  La rama permite desarrollar la nueva versión en paralelo y comparar.

Operaciones:
  should_branch(change_type, requires_regeneration) → bool

  create_branch(parent_id, branch_name) → (branch_id, branch_dir)
    Copia: source/, blueprint.json, architecture.json, execution_plan.json
    Ajusta metadata.json con id nuevo, parent_id, state="branch"

  list_branches(parent_id) → list[dict]
    Campos: branch_id, branch_name, state, created_at

  promote_branch(parent_id, branch_id)
    Copia source/ de la rama de vuelta al proyecto principal.
    Actualiza state del proyecto principal → "done".

  run_both_and_compare(parent_id, branch_id, run_command, install_command)
    Ejecuta ambas versiones en paralelo (ProjectRunner + SmokeTester).
    Retorna comparación con scores y recomendación de cuál usar.

────────────────────────────────────────────────────────────────────────────────
 11. MANEJO DE ERRORES
────────────────────────────────────────────────────────────────────────────────

──── Errores transitorios (reintentos automáticos) ─────────────────────────────

  Prefijos reconocidos como transitorios:
    ERROR:RATE_LIMIT:   — límite de tasa de API alcanzado
    ERROR:OVERLOADED:   — servicio sobrecargado
    ERROR:CONNECTION:   — error de red/conexión

  Estrategia de reintento (backoff exponencial):
    Intento 1: esperar  5 segundos
    Intento 2: esperar 15 segundos
    Intento 3: esperar 30 segundos
    Intento 4: esperar 60 segundos
    Intento 5: esperar 90 segundos
    Intentos 6-8: esperar 120 segundos cada uno
    Máximo: 8 intentos totales por llamada

──── Fallos de generación de código ────────────────────────────────────────────

  Si los 9 niveles de escalación fallan para un archivo:
    - Se guarda el archivo con validated=False
    - Se emite evento PIPELINE_ERROR con severidad "CRÍTICO"
    - El pipeline CONTINÚA (no aborta)
    - Al finalizar se reportan todos los archivos no validados

──── Ciclos en el grafo de dependencias ────────────────────────────────────────

  Se detectan por DFS antes de planificar.
  Se rompen eliminando aristas de ciclo.
  Los broken_edges se reportan en el plan y en los logs.
  El pipeline nunca falla por un ciclo de dependencias.

──── Proveedor de IA no disponible ─────────────────────────────────────────────

  Si el proveedor primario falla → se intenta el siguiente en la cadena
  de routing (ver sección 4).
  Si toda la cadena falla → error transiente con reintento o fallo del módulo.

──── Servidor ya en uso (puerto 8000) ──────────────────────────────────────────

  Si el puerto 8000 ya está en uso al iniciar:
    - Se detecta el error OSError 10048 (Windows)
    - Se loguea "reusing existing server"
    - El launcher continúa y abre la UI sobre el servidor existente

──── Errores de TTS ────────────────────────────────────────────────────────────

  Si no hay voz de referencia registrada → RuntimeError con mensaje claro.
  Si f5_tts no está instalado → is_available() retorna False y TTS se omite.
  Los errores de TTS son no-críticos y nunca bloquean el pipeline.


────────────────────────────────────────────────────────────────────────────────
 12. SISTEMA TTS (TEXT-TO-SPEECH)
────────────────────────────────────────────────────────────────────────────────

Motor: F5-TTS con modelo jpgallegoar/F5-Spanish
Archivo: kernel/tts/kokoro_tts.py
Clase: KokoroTTS (singleton thread-safe)
Sample rate: 24.000 Hz
Descarga: automática desde HuggingFace en primer uso

Parámetros de calidad de inferencia:
  _NFE_STEP      = 64      — pasos de difusión (64=máxima calidad, ~2x más lento que 32)
  _CFG_STRENGTH  = 2.5     — guidance clasificador-libre (más alto = más fiel a la voz)
  _SWAY_COEF     = -1.0    — coeficiente de muestreo sway negativo (mejora naturalidad)
  _TARGET_RMS    = 0.15    — normalización de volumen de salida (default 0.1 era muy bajo)
  _CROSS_FADE    = 0.15    — duración del cross-fade entre lotes (segundos)

Temporización del español:
  _CHARS_PER_SEC = 11.0    — caracteres por segundo a speed=1.0
  Justificación: F5-TTS nativo usa longitud en bytes UTF-8 lo que sobre-asigna
  tiempo para caracteres acentuados (ó = 2 bytes, 1 fonema). 11.0 chars/sec
  da ~20% de margen de seguridad para evitar audio cortado al final.

Recorte de silencio (sin I/O en disco):
  _SILENCE_AMP        = 0.003   — umbral de amplitud (~-50 dBFS)
  _SILENCE_MARGIN_MS  = 80      — ms de contexto antes/después del habla
  Algoritmo: máscara numpy sobre abs(wav), busca primer/último sample activo,
  mantiene margen de 80ms. Equivalente a pydub remove_silence_for_generated_wav
  pero 100% en memoria.

Limpieza de texto antes de síntesis:
  - Elimina bloques de código (``` ... ```) e inline code
  - Elimina formato markdown (*_~#)
  - Elimina URLs
  - Expande plurales entre paréntesis: error(es) → errores, duda(s) → dudas
  - Expande abreviaciones: Ej. → ejemplo:, Aprox → aproximadamente, etc.
  - Corrige dígrafo QU: qu+e/i → k (fonética española)
  - Elimina emojis y caracteres no-latinos (conserva áéíóúüñ¿¡)
  - Colapsa espacios múltiples

Voces personalizadas:
  Ubicación: kernel/tts/voices/{nombre}.wav + {nombre}.txt
  .wav — audio de referencia (voz a clonar)
  .txt — transcripción del audio de referencia

Gestión de voces:
  list_voices()           → {builtin: [], custom: [...], active: ..., speed: ...}
  set_voice(nombre)       → guarda en soda_config.json
  set_speed(velocidad)    → clamped [0.5, 2.0], guarda en soda_config.json
  delete_voice(nombre)    → elimina .wav y .txt, activa otra voz disponible

Conversión a OGG Opus (para Telegram):
  wav_to_ogg_opus(wav_bytes) → usa ffmpeg subprocess
  Bitrate: 64k, VBR on, compression_level 10
  Requiere: ffmpeg en PATH

Control de TTS:
  tts_enabled()          → UI/consola TTS (desactivado por defecto)
  tts_telegram_enabled() → TTS en Telegram (activado por defecto)

Parches aplicados al importar:
  _patch_torchaudio_soundfile() — reemplaza torchaudio.load con soundfile
  cuando torchcodec no está disponible (sin FFmpeg DLLs en Windows)
  _patch_f5tts_spanish_text_norm() — evita que jieba (tokenizador chino)
  fragmente palabras españolas con tildes


────────────────────────────────────────────────────────────────────────────────
 13. SISTEMA DE NOTIFICACIONES
────────────────────────────────────────────────────────────────────────────────

El orquestador emite eventos en tiempo real mediante _notify():
  - WebSocket → UI del browser (ui/websocket_handler.py)
  - Telegram → bot @Soda_black_bot (chat_id: 7349653298)

La función _notify() usa timeout=0.05s (fire-and-forget).
NUNCA bloquea el pipeline independientemente de si la UI está conectada.

Tipos de eventos emitidos:
  LOG              — mensaje de log general
  AI_WORKING       — una IA está procesando
  AI_ERROR         — error de IA
  FILE_GENERATED   — archivo generado exitosamente
  HEALTH_WARN      — advertencia del monitor de salud
  COPILOT_SUGGESTION — Copilot sugiere una corrección
  COPILOT_APPLIED  — sugerencia de Copilot aplicada
  COPILOT_REJECTED — sugerencia rechazada
  USER_QUESTION    — se necesita input del usuario
  START            — inicio del pipeline
  DONE             — pipeline completado con éxito
  FAILED           — pipeline falló
  PIPELINE_ERROR   — error no fatal en el pipeline
  PHASE_START      — inicio de una fase
  REFOUND_SUGGESTED — el monitor sugiere comprimir contexto

TTS del frontend (mensajes de voz al usuario):
  DONE        → "La generación del proyecto ha finalizado con éxito.
                 Puede ejecutarlo desde el panel de lanzamiento."
  FAILED      → "El pipeline de generación ha fallado. Revise la consola
                 para obtener más detalles sobre el error."
  ITERATION_DONE → "La iteración número N ha finalizado. Puede ejecutar
                 la aplicación para verificar los cambios."
  USER_QUESTION → lee la pregunta al usuario

Reglas de texto para TTS (estrictas):
  1. Oraciones completas — nunca texto cortado ni frases incompletas
  2. Sin diminutivos ni coloquialismos (no "listo", no "ejecutalo")
  3. Sin strings técnicos crudos (rutas, códigos de salida, guiones bajos)
  4. Sin guiones bajos en nombres de proyecto
  5. Condicionales explícitos — fallback fijo si variable puede ser vacía

────────────────────────────────────────────────────────────────────────────────
 15. COPILOT (REVISIÓN ITERATIVA DE CÓDIGO)
────────────────────────────────────────────────────────────────────────────────

El "Copilot" en SODA es un módulo de revisión que corre sobre el código
generado para detectar y corregir problemas antes de finalizar.

Temperatura (configurable por proyecto):
  baja  → 1 pasada de código, sin regeneración de fases
  media → 3 pasadas de código, 1 regeneración de fase (DEFAULT)
  alta  → 5 pasadas de código, 2 regeneraciones de fase

Loop Qwen↔Copilot (_dev_qwen_copilot_loop):
  1. CodeGenerator genera el módulo
  2. CopilotConsultant revisa el código generado
  3. Si hay problemas:
     a. CopilotConsultant intenta corregirlo directamente (fix_module_code)
     b. O el feedback se pasa a Qwen para regeneración
  4. En la última pasada + problemas restantes:
     → verify_module_code (verificación final de Copilot)
     → correcciones finales de Copilot

Revisión adicional por intensidad:
  Si intensity_level = "high" o "critical":
    Claude o Gemini hacen una revisión extra del código generado
    para detectar problemas que Qwen/Copilot podrían haber pasado.

────────────────────────────────────────────────────────────────────────────────
 24. DECISIONES DE ARQUITECTURA CRÍTICAS (NO CAMBIAR SIN ANÁLISIS)
────────────────────────────────────────────────────────────────────────────────

  1. _notify() timeout=0.05s
     → Si se aumenta, bloquea el pipeline.
     → Es fire-and-forget intencional.

  2. load_dotenv() explícito en cada entry point
     → Sin esto, las API keys NO se cargan desde la UI webview.
     → NO eliminar ni mover a un único punto centralizado.

  3. DockerSandbox usa npipe (Windows)
     → NO usar unix socket. Windows 11 no tiene /var/run/docker.sock.

  4. field "dependencias" en architecture.json
     → Deben ser nombres exactos del campo "nombre" de otros módulos.
     → Rutas de archivo y librerías externas NO van aquí.
     → El DependencyGraph filtraría cualquier nombre que no exista como módulo.

  5. Qwen como primera línea de generación
     → Es gratuito y rápido para archivos simples.
     → La escalación a cloud solo ocurre cuando Qwen falla 3 veces.
     → NO saltear Qwen para todos los archivos, solo los clasificados como complejos.

  6. validated=False no aborta el pipeline
     → Diseño intencional: un archivo difícil no debe detener todo el proyecto.
     → El reporte final lista todos los archivos no validados.

  7. Temperatura de Claude deprecated
     → Claude 4.x no acepta el parámetro temperature en la API.
     → El driver lo acepta por compatibilidad pero no lo envía.
