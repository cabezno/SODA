# Learnings from proj_20260420_231044
*2026-04-20*

## Pattern: Decoupled Alert and Event Logic
Separating the 'Alerts' module from the 'Events' module, treating alerts as sub-resources of events (e.g., POST /events/{id}/alerts), worked well. This allows for flexible alert management (multiple reminders per event) and keeps the core Event model clean and focused on the event itself.

## Pattern: Modular, Resource-Oriented API
The clear division of the API into resource-based modules (Users, Events, Alerts, Notifications) is a highly effective pattern for this type of CRUD-heavy application. It aligns well with FastAPI's structure, promotes separation of concerns, and makes the API predictable and easy to consume.

## Pattern: Scheduler for Time-Based Actions
Using a background scheduler (like the suggested APScheduler) is the correct pattern for handling asynchronous, time-based tasks like sending reminders. This avoids blocking the main application thread and ensures reliable delivery of notifications without impacting API performance.

## Anti-pattern: Using SQLite for Concurrent Operations
While suitable for development, SQLite is a problematic choice for a multi-user application featuring a background scheduler. Concurrent writes from user requests and the scheduler can easily lead to 'database is locked' errors. A client-server database like PostgreSQL should be preferred for production to handle concurrency gracefully.

## Preference: Stateless JWT Authentication
The choice of JWT for session management indicates a preference for stateless authentication. This simplifies the backend by not needing to store session state, which is ideal for scalable, RESTful APIs.

## Preference: Monolithic but Modular Backend
The architecture points to a preference for a monolithic structure where all logic resides in a single FastAPI application. However, the strict internal modularization shows a desire for organization and maintainability without incurring the complexity of a microservices architecture.

## Preference: Explicit Creator-Based Permissions
The requirement that only the creator of an event can edit or delete it shows a preference for a simple, ownership-based authorization model over more complex role-based access control (RBAC), which is appropriate for this project's scope.

## Knowledge Suggestion
Integrating and managing background schedulers (e.g., APScheduler, Celery) with FastAPI for handling asynchronous and time-based tasks such as sending notifications and emails.
