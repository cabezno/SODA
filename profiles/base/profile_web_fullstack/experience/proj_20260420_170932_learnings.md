## Pattern: Layered API Structure (Router -> CRUD -> Model)
The separation of concerns into `routers` (API interface), `crud` (data access logic), and `schemas/models` (data representation) was highly effective. This pattern keeps the codebase clean, testable, and easy to navigate, which is ideal for RESTful CRUD applications.

## Pattern: Integrated Static Frontend
Serving the vanilla JavaScript frontend directly from FastAPI using `StaticFiles` is a simple and powerful pattern for self-contained applications. It eliminates the need for a separate web server (like Nginx) or complex CORS configurations during development and for simple deployments.

## Pattern: Async-first Stack
Employing a fully asynchronous stack (FastAPI, SQLAlchemy with asyncpg/aiosqlite) from the outset is a robust pattern even for simple projects. It ensures high performance for I/O-bound operations and provides a scalable foundation without premature optimization.

## Preference: Simplicity over Frameworks (Frontend)
A clear preference for vanilla HTML/CSS/JS was shown for a simple UI, despite the profile having React skills. This indicates a pragmatic approach, avoiding the overhead of a complex framework when the requirements don't justify it.

## Preference: Environment-based Configuration
The use of `pydantic-settings` reveals a preference for separating configuration from code, following 12-Factor App principles. This makes the application more portable and easier to manage across different environments (dev, staging, prod).

## Preference: Explicit Data Contracts
The detailed use of Pydantic schemas (`TaskCreate`, `TaskRead`, `TaskUpdate`) for input validation and output serialization shows a preference for strong, explicit data contracts at the API boundary. This improves API robustness and documentation.

## Knowledge Suggestion
Using FastAPI's `lifespan` async context manager to manage application-level resources, such as initializing and closing database connection pools.
